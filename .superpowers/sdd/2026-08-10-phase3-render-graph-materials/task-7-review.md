## 2. Scrutiny points — detailed findings

### 2.1 `setTexture()`'s silent fallback (highest-scrutiny item 1) — **real defect, confirmed**

`MaterialInstanceImpl::setTexture()` (`api_impl.cpp`) does exactly what the coordinator suspected: it QIs the passed `IRxTexture*` for a private, engine-internal GUID (`kIID_InternalTextureBridge`) to distinguish a real, `createTexture2D()`-backed texture from anything else, RTTI-free — this detection mechanism itself is COM-correct and exactly what the coordinator's own suggested fix would use. The defect is in the *policy* applied when that QI fails: instead of rejecting the call, `bindlessIndex` stays `0` and the write proceeds with `RX_OK`:

```cpp
uint32_t bindlessIndex = 0;
void* bridgeOut = nullptr;
if (texture->queryInterface(kIID_InternalTextureBridge, &bridgeOut) == RX_OK && bridgeOut != nullptr) {
    bindlessIndex = static_cast<IInternalTextureBridge*>(bridgeOut)->bindlessIndex();
}
```

Index `0` is not a sentinel — it is a real, valid bindless slot that will hold whatever texture happened to be registered first. A caller that passes a non-engine `IRxTexture` (including, today, a bug where the wrong pointer type is passed, or a future third-party `IRxTexture` implementation) gets **silently wrong rendering with zero diagnostic signal** — exactly the "debugging nightmare" the coordinator flagged. `rx_api.h`'s own `IRxTexture` doc comment states plainly that it "always wraps a renderer-owned `rhi::Texture2D` + bindless-table handle, created via `IRxMaterialSystem::createTexture2D()`" — i.e., the ABI's own documented contract already assumes no other kind of `IRxTexture` is legitimate input. Rejecting one with `RX_E_INVALIDARG` on QI failure is therefore not a new restriction; it is enforcing an invariant this header already claims to hold.

The implementer's stated reason for keeping the fallback — preserving Task 6's `FakeTexture`-based refcount tests unchanged — does not hold up under inspection: `kIID_InternalTextureBridge` is declared inside `api_impl.cpp`'s anonymous namespace, so it is **unreachable from any test file** regardless of policy; no test double could ever answer it. Task 6's `FakeTexture` tests exercise an input shape (a bare, non-engine `IRxTexture`) that the ABI's own documentation says should never occur. Fixing this does not cost real coverage: Task 7 already added a REAL-texture-based test for the identical refcount+bindless-index behavior (`test_api_factory.cpp`'s "createTexture2D creates a real texture; setTexture writes its REAL bindless index" case) — the only cost of rejecting non-engine textures is updating/retiring the *older* Task 6 `FakeTexture`-based assertions that currently expect `RX_OK`.

**Severity: High.** Not Critical — no crash, no memory corruption, no spec violation, and the report's own honest disclosure notes Task 8's sample 06 will only ever pass real `createTexture2D()`-backed textures, so there is no live exploitation path today. But it is a genuine, code-verifiable defect in the ABI's own error-handling contract, on exactly the axis ("errors are `RxResult` codes, never silent wrong behavior") this codebase otherwise holds to rigorously, and the fix is small and mechanical.

### 2.2 Reload teardown lifetimes (highest-scrutiny item 2) — **verified correct against the real Vulkan spec text**

The implementer's claim — that `PipelineLayoutBundle` (pipeline layout + descriptor set layouts) may be destroyed immediately on reload, unlike `VkPipeline`, because these object types only need to remain valid through creation/recording, never through GPU execution — was checked against the actual Vulkan spec source, not recollection. Pulled `chapters/descriptorsets.adoc` directly from `KhronosGroup/Vulkan-Docs`:

- `vkDestroyPipelineLayout`'s entire Valid Usage block (`VUID-vkDestroyPipelineLayout-pipelineLayout-00299`/`-00300`) contains **only** allocation-callback-matching constraints — no VUID requires the layout to outlive command buffers recorded against pipelines built from it, in-flight or not.
- `vkDestroyDescriptorSetLayout`'s entire Valid Usage block (`VUID-vkDestroyDescriptorSetLayout-descriptorSetLayout-00284`/`-00285`) contains the **same** — only allocation-callback matching. No VUID requires the layout to outlive descriptor sets allocated from it, or pipeline layouts built from it, whether or not those are still referenced by pending command buffers.
- The only lifetime language anywhere near this area of the spec is a narrower rule about *immutable sampler handles* specifically ("the sampler objects must not be destroyed before the final use of the set layout and any descriptor pools and sets created using it") — this is about the `VkSampler` objects a set layout may copy handles from, not about the set layout's own lifetime, and this codebase's material `TParams` blocks use no immutable samplers.

This confirms **both halves** of the coordinator's question: (a) yes, legal while command buffers recorded with the old pipeline layout are pending execution, and (b) yes, legal while descriptor sets allocated from the old descriptor-set layout are still live and potentially bound in pending command buffers. This matches the same general Vulkan pattern already established in this codebase for `VkShaderModule` (cited correctly in the code's own comment) — creation-time-consumed "template" objects that dependent objects (`VkPipeline`, `VkDescriptorSet`) do not hold a live back-reference to. `VkPipeline` itself is the one object in this teardown that command execution genuinely does reference for its duration, which is exactly why (and only why) it alone goes through the `DeletionQueue`. **No finding — the implementer's citation and reasoning are correct**, and the ordering in `reloadChanged()` (retire stale `VkPipeline`s first, then destroy old shader modules, then move-assign the new `PipelineLayoutBundle` over the old, whose `operator=` destroys the old one first) has no gap: no future `getPipeline()` call can ever be issued against the old, now-destroyed shader modules, since `record->contentHash` has already moved to the new hash by that point.

### 2.3 Frames-in-flight correctness of the arenas (highest-scrutiny item 3) — **correct by construction; real test-coverage gap**

Walked the full path: `ParamArena::beginFrame(frameIndex)` selects slot `frameIndex % framesInFlight()` for both the byte-arena cursor and the paired `DescriptorArena`'s pool — the same slot-selection rule everywhere else in this codebase (`FrameSync`, `DescriptorArena` itself) that the "caller only advances after its own fence wait" contract depends on. `writeAndAllocate()` bump-allocates only within the *current* frame's slot; the bounds check (`end > buffer.size()`) happens strictly before any `memcpy`, so exhaustion cannot corrupt memory — it returns `VK_NULL_HANDLE` (logged), which `bindInstance()` converts to a `std::runtime_error`. Descriptor-pool exhaustion (`kMaxInstancesPerFrame`) is handled identically one layer down. This is genuinely fail-safe, not fail-silent, and documented limits exist (`kBytesPerFrame = 1 MiB`, `kMaxInstancesPerFrame = 512`).

However: **`ParamArena` itself has no standalone unit test.** `instance.h`'s own header comment states it "[l]ives at namespace scope... so it can be unit-tested on its own," but grepping the delivered diff shows `ParamArena` is referenced only from `instance.cpp`/`material_system.cpp`/`material_system.h` — every exercise of it in the test suite goes through `MaterialSystem::bindInstance()`, and every one of those calls uses `frameInFlightIndex = 0` exclusively (`test_material_system.cpp`'s two `bindInstance()` cases, both `system->beginFrame(0, ...)`). Nothing in the delivered tests advances `ParamArena` to a second frame-in-flight slot, confirms slot isolation at this composed layer, or drives the byte-arena/descriptor-pool to exhaustion through `bindInstance()` itself to confirm the documented throw path is actually reachable in practice (as opposed to reasoned about). The underlying primitive (`DescriptorArena`) *is* independently, thoroughly tested for exactly this at the `rx_rhi_vk` layer (3 simulated frames, reset-reclaim, exhaustion) — so the risk of an actual bug here is low — but the report's own claim of testability at this layer is not backed by a delivered test, and this is precisely the axis flagged as needing the deepest scrutiny.

**Severity: Medium.** No evidence of an actual bug — the composition is simple and the sub-primitive is well-tested — but a real, unaddressed gap in verification depth on the highest-scrutiny axis, and an overclaim in the header comment relative to what was actually delivered.

### 2.4 Reflection collapse (highest-scrutiny item 4) — **confirmed, verified by absence**

Offsets used by the blob are therefore provably sourced from the identical reflection object that produced the pipeline's real SPIR-V — not merely "should agree by inspection," as was the caveat in Task 6's second-session design. ## 3. Findings by severity

**F1 — High. `setTexture()`'s silent bindless-index-0 fallback for non-engine `IRxTexture` instances.**
A texture that fails the internal `kIID_InternalTextureBridge` QI (any `IRxTexture` not created via `IRxMaterialSystem::createTexture2D()`) causes `setTexture()` to write bindless index `0` — a real, arbitrary slot — into the instance's blob and return `RX_OK`, rather than `RX_E_INVALIDARG`. `rx_api.h`'s own `IRxTexture` doc comment already documents that a valid `IRxTexture` "always" wraps an engine-created texture, so rejecting anything that fails this check enforces a contract the header already claims, not a new one. Silent wrong-texture binding with zero diagnostic signal is a serious debuggability defect on a public ABI surface. The one cited reason for keeping the fallback (preserving Task 6's `FakeTexture` refcount tests) does not hold: the internal bridge GUID is anonymous-namespace-private and unreachable from any test double regardless of policy, and Task 7 already added an equivalent real-texture test that would retain full coverage after a fix. Recommended fix: return `RX_E_INVALIDARG` when the QI fails, and update/retire the `FakeTexture`-based `setTexture` assertions in `test_api_factory.cpp` that currently expect `RX_OK` for a non-engine texture.

**F2 — Medium. `ParamArena`'s frames-in-flight isolation/exhaustion has no standalone test, despite the header's own claim that it "can be unit-tested on its own."**
Every exercise of `ParamArena` in the delivered test suite goes through `MaterialSystem::bindInstance()` at `frameInFlightIndex = 0` only — no test advances it to a second frame-in-flight slot to confirm slot isolation at this composed layer, and no test drives the byte-arena or its paired `DescriptorArena` to exhaustion *through* `bindInstance()` to confirm the documented `std::runtime_error` path is actually reachable in practice. The underlying `DescriptorArena` primitive is independently, thoroughly tested for exactly this at the `rx_rhi_vk` layer, which keeps the real-bug risk low, but this is precisely the axis the coordinator flagged for the deepest scrutiny, and the gap is real relative to both the brief's spirit and the header's own claim.

**Positive/no-finding items, scrutinized as hard as the two findings above and confirmed sound:** the reload-teardown Vulkan-spec legality question (§2.2, checked against the actual `Vulkan-Docs` VUID text, not recollection), the reflection-collapse's offset/pipeline consistency (§2.4, verified by absence and by tracing both consumers to the identical reflection object), hot-reload invalidation completeness (§2.5), `DescriptorArena`'s own exhaustion/reset behavior (§2.6), and the `bindInstance()` test rig's architectural necessity (§2.7).

### Item 3 — `writeAndAllocate()`'s byte-cursor advances before a possible `DescriptorArena::allocate()` failure: **acceptable as documented; no fix warranted**

Independently traced the exact sequence in `instance.cpp`: the byte-arena bounds check (`end > buffer.size()`) happens *before* any write, so an oversized request is rejected with the cursor untouched — the only waste path is a request that fits the byte budget (cursor advances, `memcpy`/`flush` happen) but whose *subsequent* `DescriptorArena::allocate()` call then fails. This is real, but bounded and non-compounding into a materially worse outcome, for a reason not stated in the report: `DescriptorArena`'s pool is a fixed-`maxSets`, non-update-after-bind pool serving only ever the identical set layout/binding shape (one `VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER` at binding 0) — for that shape, `vkAllocateDescriptorSets` exhausts **monotonically**: it cannot spuriously fail before the pool's real capacity (512, exactly `kMaxInstancesPerFrame`) is reached, and it cannot recover after failing once within the same `beginFrame()` cycle. Two consequences follow:

1. **No legitimate (within-documented-limits) call can be made to fail "prematurely" by this waste.** Every one of the first 512 `writeAndAllocate()` calls in a frame is guaranteed to succeed at the `DescriptorArena` step (capacity not yet reached) regardless of any byte-arena waste from earlier calls in the same frame, since 512 aligned allocations at realistic `TParams` sizes consume on the order of 128 KiB of the 1 MiB budget — nowhere near enough to starve the 512nd legitimate call even in a worst-case per-call size.
2. **Waste only accumulates on calls that were already past the documented per-frame ceiling and therefore already going to fail one way or another** (either at the `DescriptorArena` step, as they do today, or — if a caller went abusively far past 512, on the order of another ~3500 additional over-limit calls at typical sizes — eventually at the byte-arena's own bounds check instead). Both outcomes are the identical clean `VK_NULL_HANDLE` (logged, no corruption); which specific check trips first is immaterial to the caller, who was already outside the documented contract.

**Rating: acceptable as-is, correctly left undone.** This is real, minor, efficiency-only technical debt with no plausible sequence — including a deliberately abusive one — that turns it into premature exhaustion of a call the documented contract promises to succeed, or into anything worse than the already-clean failure mode. The implementer's own disclosure (flagged explicitly for the record rather than silently patched or silently ignored) is the right call; a cursor-rollback-on-failure refinement remains a legitimate, low-priority future cleanup, not a defect blocking sign-off.
