## The central question: texture path vs. texture sampling

**(a) What is actually delivered, traced through the real code:**

1. `createScene()` (`main.cpp:813-825`) generates an 8×8 procedural RGBA8 checkerboard and calls the public `IRxMaterialSystem::createTexture2D()` — succeeds, returns a real `IRxTexture*`.
2. For both `checker.slang` instances, `obj.instance->setTexture("checkerTexIndex", scene.checkerTexture)` is called (`main.cpp:872`) — a genuine public-API call.
3. Traced into `api_impl.cpp:344-411` (`MaterialInstanceImpl::setTexture`): validates `"checkerTexIndex"` against the material's own Slang reflection (`material_system.cpp`'s `classifyFieldKind()` maps a `uint` scalar field to `MaterialParamKind::TextureIndex` — confirmed at `material_system.cpp:203-216`), recovers the texture's **real** bindless index via an internal `queryInterface` bridge (rejecting any non-engine-created `IRxTexture`, per the Task-7 F1 fix), and `memcpy`s that real `uint32_t` bindless index into the instance's CPU-side parameter blob at the reflected offset.
4. That blob is exactly what `materialBridge::bindAndGetLayout()` (the marked draw-time bridge) passes into `MaterialSystem::bindInstance()`, which copies it into the real per-instance UBO bound at descriptor set 1 for the actual `vkCmdDrawIndexed` call `recordDraws()` issues.

So the chain **create → set → validate → recover real bindless index → write into blob → bind into a real GPU-visible UBO for a real draw call** is genuine, verified by reading the actual implementation (not just the sample), not merely asserted by the report.

**Where it stops:** `checker.slang`'s `evaluate()` (`materials/checker.slang:78`) reads `gParams.checkerTexIndex` only as `color.w += float(gParams.checkerTexIndex) * 0.0` — a genuine (not compiler-folded, since it's a runtime uniform read) but numerically inert read. It never calls `.Sample()` against any texture array. Tracing *why* not: `shaders/material/material.slang` and `forward_entry.slang` (the shared modules every material links against) declare no bindless resource of any kind — a material module only ever sees `MaterialVertex` (`worldPos`/`normal`/`uv`) and its own `gParams` block. `MaterialSystem::reflectMaterialLayout()` (`material_system.cpp:300-321`) walks the **entire linked program's** top-level globals and hard-rejects anything that isn't exactly one `ParameterBlock<...> gParams` — verified directly by reading the loop, not inferred: the very first non-`ParameterBlock` top-level global found is an immediate compile failure, regardless of which module (shared or per-material) declared it. So even if `material.slang` itself declared a shared bindless array, today's reflection would reject the composite program outright. The chain stops precisely there: **no shading-language access point exists, and the one thing that would need to change to create one (the reflection allow-list) is in `rx_material` core, not in this sample.**

**(b) Is this a defensible reading of the requirement, or a real miss?**

Defensible, not a miss — for four concrete reasons, weighed honestly:
- The literal wording is "the public texture **path** is exercised end-to-end," and a path most naturally means the API call chain (create → set → validate → GPU-visible), which is fully and verifiably true here — not "the texture visibly changes a rendered pixel."
- This is not a novel scope call the implementer invented under pressure: `src/rx_material/tests/data/test_textured.slang`'s `albedoIndex` field already established the identical "read numerically, never sample" pattern in Task 7, before this task ever started. `checker.slang` explicitly cites that precedent rather than asserting a new one.
- It was disclosed prominently and proactively in three independent places — the report's own "Concerns" section, `checker.slang`'s header comment, and `main.cpp`'s header comment — not buried or discovered only under review scrutiny.
- Nothing about the disclosure is evasive: the report explicitly states the fix would require "changing `rx_material`'s core reflection rules, not just this sample," correctly identifying the boundary rather than hand-waving it.

That said, this is genuinely the softer end of "end-to-end," and calling it out as a finding (not a checklist failure) is the right level of scrutiny: a future reader skimming "texture path exercised end-to-end" without the caveat could reasonably assume the texture affects the image. See Finding F1.

**(c) Scope of actually wiring real sampling, traced concretely (not estimated abstractly):**

Confirmed by reading the relevant files directly:
- `rx::rhi::BindlessTable` (`src/rx_rhi_vk/include/rx_rhi_vk/bindless.h:82-91`) already exposes a real, working three-binding descriptor-set-0 layout: binding 0 = `VK_DESCRIPTOR_TYPE_SAMPLED_IMAGE` (an unbounded `Texture2D[]`), binding 1 = `VK_DESCRIPTOR_TYPE_SAMPLER` (a separate `SamplerState[]`), binding 2 = a storage-buffer array. `src/rx_rhi_vk/src/context.cpp:145`'s own "known false positive" comment ("validation layer's sync validation misclassifies a separate-sampler `Texture2D.Sample()` read") confirms this separate-sampler bindless pattern is **already proven working elsewhere in this codebase** — this is not new R&D, it is wiring an already-solved RHI-side mechanism into a new shading-language contract point.
- What's actually missing, concretely: (1) `material.slang`/`forward_entry.slang` need a shared declaration of that same `Texture2D[]`/`SamplerState[]` pair at set 0, matching `BindlessTable`'s real binding numbers; (2) `reflectMaterialLayout()` (`material_system.cpp:300-321`) needs a second recognized top-level-global shape (today it accepts exactly one `ParameterBlock` and rejects everything else, full stop) — a real, deliberate change to `rx_material`'s core reflection allow-list, not a one-line patch, since it has to keep rejecting genuinely unsupported globals while allowing exactly this one known shape; (3) at least one material's `evaluate()` needs to actually call `.Sample()`; (4) a new GPU test proving the rendered pixel actually changes with texture content (today, no test in the codebase exercises this at all).

This is a real, bounded feature task that touches `rx_material` core (2 shared shader files + the reflection function + at least one material + a new test) — bigger than a same-day fix-round patch, but narrower than Phase 4's full StandardPBR effort (which needs multiple textures per material, normal mapping, a roughness/metalness workflow, and likely a materially different resource-binding convention besides). **Recommendation: an explicit, separately-ledgered task — "wire real bindless texture sampling into `rx_material`'s shared material contract" — landed before or alongside Phase 4's StandardPBR kickoff, not a Task 8 fix-round item, and not silently folded into StandardPBR's scope without being called out as its own prerequisite.**
