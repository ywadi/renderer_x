## Scrutiny findings

### 1. Third false-positive guard in `context.cpp` — independently verified, not suppressing a real hazard

Reproduced the implementer's entire A/B claim myself, not just read it:

- Ran `sample_05_multipass --validate` against the machine's apt-packaged 1.3.204.1 layer: got the exact `SYNC-HAZARD-READ_AFTER_WRITE` / `VK_DESCRIPTOR_TYPE_SAMPLED_IMAGE` / `SYNC_FRAGMENT_SHADER_SHADER_STORAGE_READ` / `SYNC_IMAGE_LAYOUT_TRANSITION` / `vkCmdPipelineBarrier2` message the guard's five `.find()` substrings target — both `write_barriers` variants (`SYNC_FRAGMENT_SHADER_SHADER_SAMPLED_READ` for the shadowmap read, `SYNC_COLOR_ATTACHMENT_OUTPUT_COLOR_ATTACHMENT_WRITE` for the HDR read) appear exactly as documented.
- Re-ran the identical binary with `VK_LAYER_PATH` pointed at the newer 1.4.357 build already present on this machine (`/home/ywadi/sponza/vvl/`): zero hazards, zero warnings, gate PASSED — independently confirms the report's "clean against a newer layer" claim rather than trusting it.
- Temporarily forced `isKnownSyncValidationSeparateSamplerMisclassification()` to `return false` (ablation), rebuilt, reran: the gate genuinely **FAILS** (`hasValidationErrors()` trips, `multipass headless gate FAILED`) — proving the guard is load-bearing on this machine, not a dead/unnecessary suppression. Reverted the edit; `git status`/`git diff` on `context.cpp` confirmed clean afterward.
- Guard scope: five required substrings (hazard ID, descriptor type, misclassified usage, `prior_usage`, barrier command) — a genuinely different real hazard (different descriptor type, different usage classification, or no barrier-command context at all) would not match. This is consistent with the file's existing two-guard convention (narrow substring match, not a bare hazard-ID or VUID).
- Independent reasoning on plausibility: in both observed variants, the reported `write_barriers` field already reflects a *correct* derivation for the actual consumer (`...SAMPLED_READ` for the shadowmap case; the color-attachment write for the HDR case) — i.e., rx_graph's Executor-derived barrier is present and its access mask targets the right consumer stage. The tool's *own* separate classification of the draw-time access as `STORAGE_READ` (never emitted by this codebase's shaders — every read here is `Texture2D.Sample()`, a sampled read) is what's inconsistent, not the barrier. That internal self-contradiction (correct barrier, wrong subsequent-access classification) is a strong, plausible false-positive signature for a `1.3.204`-vintage layer's known-immature interaction between descriptor-indexed bindless reads and the (at the time newer) synchronization-validation feature — not a smoking gun for a missing/wrong barrier (which would instead show an empty or unrelated `write_barriers`).
- Documentation style matches the file's first two guards: root cause, reproduction shape, what's deliberately excluded from the match and why, cross-checked evidence trail.

No residual concern here beyond a minor nit: neither this guard nor the two existing ones cite an upstream `KhronosGroup/Vulkan-ValidationLayers` issue number, which would make the "known bug, not our bug" claim independently checkable by a future reader without redoing the A/B themselves. Not blocking — the A/B methodology itself is sound and I reproduced it.

### 2. `ObjectTransform` struct-drift fix — correct, but the underlying duplication is still unguarded (finding)

- Confirmed `shadow.vert.slang`'s and `lit.vert.slang`'s `ObjectTransform` structs are now byte-for-byte identical (`float4x4 mvp; float4x4 lightMvp; float4 albedo; float4 lightDirWorld;`), matching the C++-side `struct ObjectTransform` in `main.cpp:448-453`. The fix itself is correct.
- No shared `.slang` include exists anywhere in this codebase (`shaders/` has no `.slangh`/common-include files at all — checked via `find`/`grep`), and `rx::shader::Compiler` compiles one module/string per call, so a cross-file include isn't a pattern this codebase has established yet; not inventing one here isn't a deviation from precedent.
- More significant: this codebase **does** have a live guard mechanism for exactly this class of bug — every push-constant struct in `main.cpp` is checked at runtime against `reflect()`'s reported push-range size (`sizeof(ShadowPushConstants)` etc., `main.cpp:702/833/981`) — but `rx_shader`'s `ShaderLayoutInfo`/`reflect()` (checked `shader_layout_info.h`) exposes **no** stride/size field for `StructuredBuffer` bindings at all, only for push-constant ranges. So the one tool that could have caught this exact bug automatically (a reflected-stride assert, mirroring the push-constant one) does not exist for storage buffers in this codebase — extending `rx_shader::reflect()` to expose it would be new scope, not something Task 4 could have added with existing tooling.
- Net: the fix is correct and thoroughly documented (both `.slang` files carry the full bug narrative), but three-way duplication (C++ / `lit.vert.slang` / `shadow.vert.slang`) remains guarded only by comments, with no automated re-drift guard. Partial, incidental mitigation exists: the sample's own shadow-vs-lit brightness assertion is exactly the check that caught this bug during development and would very likely (though not guaranteed) catch a recurrence, since a garbled `lightMvp` for the cube/sphere rows would probably move or destroy the shadow footprint the probes rely on. That's a side effect of the correctness gate, not a designed regression guard.
- **Severity: Low-Medium.** Not a defect in the delivered code, but a real gap the brief specifically asked to check for, and it's real: nothing but a comment stops the next edit to one of the three copies from silently reintroducing the exact bug this task's report describes finding and fixing.

### 3. Pixel-gate robustness — solid, comfortable margins, no edge fragility

- `main.cpp`'s header comment gives a closed-form derivation for both probes; independently re-derived it: cube shadow footprint in Z is `[-1, 1 + 2·1/tan(50°)] ≈ [-1, 2.68]` under azimuth-0 light; `kShadowProbeWorld=(0, 2.0)` sits centered in X (safest position — the shadow's X-extent equals the cube's own `[-1,1]` footprint at azimuth 0, so X=0 maximizes distance from either edge) and well inside the Z envelope (margin ≈0.68 on the far edge, ≈3.0 on the near edge).
- `kLitProbeWorld=(-4,-4)` is far from both the cube+shadow zone (X∈[-1,1]) and the sphere footprint (~X∈[2.5,4.5], Z∈[1.5,3.5]), and far from the ground's own edge (`kGroundHalfSize=6`).
- Empirically: observed margins are large, not borderline — shadow brightness_sum≈177 vs. lit≈451 (ratio ≈2.55×, comfortably over the 2× requirement) and 451 vs. the 153 floor (≈2.9× over). Probe pixel coordinates (128,167 and 49,49 at 256×256) are well inside the viewport, nowhere near `worldToPixel()`'s clamp boundary.
- No off-by-one or edge-adjacency risk found.
