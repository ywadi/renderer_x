## Scrutiny points

**1. Slang specialization/retention + same-module-name caveat.** Mechanism verified real
(probe #2). `record.linkedProgram = linked;` retains the linked `IComponentType` in the
`MaterialRecord` stored in the handle pool for the material's whole lifetime, mirroring
`CompileResult::linkedProgram`'s contract; no use-after-free risk (`getLayout`/
`getEntryPointCode` are both called before that assignment and don't need the retained copy to
have already happened, and the retained copy is also correctly a `Slang::ComPtr` refcount
bump, not a raw pointer). Same-module-name caveat confirmed (probe #3) to fail loudly rather
than alias silently — the concern in scrutiny point 1 is answered: no path in `MaterialSystem`
can silently alias two different materials via this caveat.

**2. `getBindingIndex()` vs `getBindingSpace()` reflection finding.** Independently reproduced
(probe #1), and the diff's implementation (`reflectMaterialLayout()`) reads the correct field.
Verified `PipelineLayoutBuilder::build()`'s actual `.cpp` (not just its header) correctly
gap-fills and substitutes: with `layoutInfo.bindings` containing only one set-1 binding and a
non-null `externalSet0`, `maxSet=1` -> `setCount=2` -> `setLayouts[0]=external`,
`setLayouts[1]` freshly created from the single `VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER` binding.
A second binding at set 1 (e.g. a future sampler in the block) would need `reflectMaterialLayout`
itself extended — it currently walks only *top-level global parameters* (one loop iteration per
Slang-reported global, i.e. exactly one entry for the whole `ParameterBlock<TParams> gParams`,
which lowers to exactly one binding at (set 1, binding 0) regardless of how many plain-data
fields `TParams` has) — so a second *plain-data* field inside `TParams` does not create a
second binding at all (Slang's own SPIR-V lowering keeps a resource-field-free
`ParameterBlock` as one UBO). A second binding would only appear if a future material puts a
resource-typed field (a `Texture2D`, say) directly inside `TParams` — that case is explicitly
out of scope today (D8 routes textures through bindless indices inside the UBO, never a
resource-typed field) and is called out by the implementer as unshipped, untested future work,
not silently mismapped. No misplacement risk for anything Phase 3 actually ships.

**3. Cache-key integrity.** `PipelineKey{moduleHash, passHash, specializationBits}` is looked
up via `std::unordered_map<PipelineKey, VkPipeline, PipelineKeyHash>` — correctness is
guaranteed by `PipelineKey::operator==` (defaulted, compares all three fields), so a
`PipelineKeyHash` collision (individually plausible with 3x FNV-1a-64 mixed together, though
FNV-1a is spec-mandated per the coordinator's own ruling, not the implementer's choice) can at
worst cost a bucket probe, never return the wrong `VkPipeline` — confirmed by reading
`std::unordered_map`'s own contract, not assumed. `specializationBits` is genuinely threaded
through end-to-end (struct field, mix, equality) even though always 0 in Phase 3. The
compile-counter evidence is real and non-vacuous: `++impl.compileCount` appears exactly once
in the file, inside `loadMaterial()`, immediately before `composite->link(...)`; `getPipeline()`
contains no Slang API calls at all (only `vkCreateGraphicsPipelines` on a miss, an early
`return it->second;` on a hit) — this is a structural guarantee from control flow, not just an
assertion the test happens to pass.

**4. PassSignature/executor population.** `executor.cpp`'s new block reuses the *same*
`colorPhysIdx`/`depthPhysIdx` classification already computed for `vkCmdBeginRendering` (order
preserved — same loop, same index order used for the real `VkRenderingAttachmentInfo` array),
reads formats from `impl.resources` (`ResolvedResource::format`, the *runtime-resolved* format,
e.g. real swapchain format for the backbuffer) rather than the compile-time declared
`AttachmentDesc::format` — this is the correct choice, since a pipeline's
`VkPipelineRenderingCreateInfo` formats must match the real bound attachment's format at draw
time or Vulkan validation flags a mismatch; confirmed structurally consistent with the
`colorAttachments`/`depthAttachment` `VkRenderingAttachmentInfo` construction just above it in
the same function, which reads the identical `impl.resources.at(physIdx)` entries. Samples are
read from `compiled.resources()[...].attachment.samples` (the device-free `PhysicalResource`,
verified to have that field via `resources.h`) since `ResolvedResource` has none — correctly
distinguished, not confused. `hash()` is explicitly *not* a raw byte scan (mixes named fields
one at a time), so the "padding" hazard the brief's constraint warns about cannot occur by
construction — this is a stronger guarantee than a raw-`memcmp`/byte-scan approach would have
given, and the header's own comment states this reasoning correctly. `colorFormats` beyond
`colorCount` is guaranteed `VK_FORMAT_UNDEFINED` by default-construction (`PassSignature
signature;` before the `if (isGraphicsPass)` block), never left uninitialized. Zero-attachment
graphics signature is rejected in `getPipeline()` with a clear `std::runtime_error` message,
matching the coordinator's ruling exactly.

**5. ci.yml exclusion regex.** Minimal, single-token addition (`rx_material_gpu` appended to
the existing `|`-alternation, matching the `rx_rhi_vk`/`rx_graph_gpu` substring-match
convention exactly) with a consistent comment update. Per `progress.md`, this has a known,

**6. `RX_MATERIAL_SHADER_DIR`.** Confirmed against `shaders/CMakeLists.txt`'s real content:
the existing project precedent (`RX_TRIANGLE_VERT_SPV`/`RX_TRIANGLE_FRAG_SPV`, baked absolute
build-tree paths for `shader_spirv_test`) is real, not invented for this comparison.
`target_compile_definitions(rx_material PRIVATE RX_MATERIAL_SHADER_DIR=...)` is `PRIVATE`, so
it is invisible to any downstream consumer's own translation units — it only affects
`MaterialSystem::create()`'s own internal shared-module search path, confined to this
library's own implementation and its own tests. Correctly and explicitly flagged by the

**7. Error paths.**

- Zero-attachment rejection: present, clear message, matches the ruling.
- Pipeline-cache corrupt-file resilience: the file-*read*-failure half is directly readable,
  ordinary, correct C++ (open-check, `!in` guarded read, warn-and-fall-back-to-empty). The

  defect; the code path itself is sound both by inspection and by direct, independent probing
  against a real device.

## Additional finding from independent code reading (not covered by the seven scrutiny points, but load-bearing)

While tracing `HandlePool`'s own known instability (already correctly documented and worked
around by the implementer for `~MaterialSystem()`'s destructor — see `Impl::materialHandles`'s
comment, which is accurate: `HandlePool::acquire()` backs its slots with a plain
`std::vector`, so a `push_back` on growth reallocates and invalidates every previously-returned
pointer into it), I checked whether the same hazard reaches the *public* API surface.
`MaterialSystem::layoutInfo(MaterialHandle) const` returns `const rx::shader::ShaderLayoutInfo&`
— a live reference into `HandlePool<MaterialTag, MaterialRecord>`'s backing vector. A caller
that holds this reference across a subsequent `loadMaterial()` call (a plausible usage pattern:
load material A, inspect its layout, then load material B for comparison) risks the reference
dangling if that second `acquire()` triggers a vector reallocation — `std::vector::push_back`
provides no pointer/reference stability guarantee across growth. `pipelineLayout()` and
`moduleHash()` are not at risk (they return plain values, `VkPipelineLayout`/`uint64_t`, copied
out before returning), so only `layoutInfo()` is exposed to this. Not exercised by the current
test suite (the one caller of `layoutInfo()` in `test_material_system.cpp` uses it once,
immediately, with no interleaved `loadMaterial()` call), and not a functional bug in anything
Task 5 itself does — but it is an undocumented sharp edge on a public accessor, in a codebase
that is otherwise scrupulous about documenting exactly this class of hazard everywhere else it
appears (e.g., the `Impl::materialHandles` comment two members below it makes the identical
argument correctly, but the public header's `layoutInfo()` doc comment says nothing about it).

## Quality verdict

**Approved, with 2 findings (both Minor, non-blocking).**

1. **Minor** — No automated test exercises `MaterialSystem::create()`'s corrupt-pipeline-cache-content
   resilience path (only "file absent" and "valid file" are covered by `pipeline-cache-persists`).
   The behavior is correct by inspection and independently confirmed against a real driver in this
   review, but a future regression in that path would go undetected by this test suite. Suggested
   fix: one additional test case that writes garbage bytes to a cache path, then asserts `create()`
   still returns non-null.
2. **Minor** — `MaterialSystem::layoutInfo()`'s returned `const ShaderLayoutInfo&` is a live reference
   into a `std::vector`-backed `HandlePool` and is silently invalidated by any subsequent
   `loadMaterial()` call that grows the pool (this hazard is already correctly identified and worked
   around elsewhere in the same file for `~MaterialSystem()`'s own internal use, but is not documented
   on this public accessor). Suggested fix: either document the caveat on `layoutInfo()` (cheapest),
   or return `ShaderLayoutInfo` by value.

Neither finding blocks merge; both are cheap to address in a fix round or can be carried forward
alongside the already-tracked concerns (RX_MATERIAL_SHADER_DIR redistribution, D8 flat-resource
reflection gap, D9 hot reload, ci.yml merge overlap with Task 4).
