## Finding verification

**1. Single source of truth — mostly satisfied; mechanism deviates from
`import`/`__include`, disclosed and technically justified.**

`shaders/multipass/scene_types.slang` exists and is the sole location of
`struct ObjectTransform` (verified: one grep hit in the whole directory).
Both `shadow.vert.slang` and `lit.vert.slang` no longer declare their own
copy — confirmed by reading both files directly. However, neither shader
consumes it via Slang's own `import` or `__include`: `main.cpp`'s
`compileAndReflect()` reads `scene_types.slang`'s bytes from disk and
textually concatenates them ahead of each pass's own file(s) *before* the
combined string ever reaches Slang — Slang itself never sees a directive.

The report states this explicitly and justifies it at length (own header
comment in `scene_types.slang`, plus `main.cpp`): a real `import`/`__include`
needs `rx::shader::Compiler`'s `slang::ISession` to carry a search path
covering the file's directory, and `Compiler::create()` sets none (verified
above) — by design (`rx_material`'s session does set one, but extending
`Compiler` to do the same was explicitly out of scope for this task; the raw
Slang API `rx_material` drives directly is a different, heavier surface this
sample doesn't otherwise touch). The chosen mechanism reuses this sample's
own pre-existing multi-file-concatenation pattern (already used to pair each
pass's vertex+fragment files) rather than inventing anything new.

Net: the actual defect (three independently-editable copies) is fully
closed, and the deviation from the literal "import or __include" ask is
transparent and grounded in verified fact, not asserted. Flagging as a
disclosed deviation, not counting it as an open item.

**2. Host drift guards — static_assert present and correct; the new
runtime probe has a real logic gap.**

- `static_assert(sizeof(ObjectTransform) == kObjectTransformShaderStrideBytes, ...)`
  is present immediately after the C++ struct (`main.cpp`), with
  `kObjectTransformShaderStrideBytes` hand-derived and the assert message
  and surrounding comment both naming `shaders/multipass/scene_types.slang`
  explicitly. This fails the build on drift, as claimed.
- The headless-gate probe (d) does target object index 1 (the cube) at its
  analytically-expected screen position via `worldToPixel(kCubePosition.xz,
  ...)`, matching the report's description.
- **Gap in `isReddish()`'s discriminating power.** The lambda is:
  ```cpp
  const bool asRgba = p[0] > p[1] + kMargin && p[0] > p[2] + kMargin;  // R=p[0] dominant
  const bool asBgra = p[2] > p[1] + kMargin && p[2] > p[0] + kMargin;  // R=p[2] dominant
  return asRgba || asBgra;
  ```
  This reduces to "index 0 is dominant OR index 2 is dominant" — i.e., "the
  dominant channel is not the middle byte." In both `VK_FORMAT_R8G8B8A8_*`
  and `VK_FORMAT_B8G8R8A8_*` (the only two conventional orderings a Vulkan
  swapchain format realistically uses here), **G always occupies byte index
  1**; only R and B trade places between index 0 and index 2. Consequently
  this check cannot distinguish a truly red-dominant pixel from a truly
  blue-dominant one in *either* real byte order — it only distinguishes
  "green/neutral-dominant" from "saturated in a non-green channel." This is
  a structural property of the code, provable from the two boolean
  expressions alone, independent of any specific runtime data.
  - Empirically corroborated with real values from this run: the actual
    swapchain format on this machine is BGRA-shaped (cube's real channels
    `(103,113,164,255)` — idx2 clearly dominant, matching R=0.75 being the
    cube's largest albedo component at real index 2). The floor's real
    near-neutral probe `(153,149,149,255)` correctly returns `isReddish() ==
    false` (neither margin condition holds) — the floor-substitution case is
    correctly rejected.
  - The gap: the sphere's albedo `(0.2, 0.45, 0.8)` is blue-dominant with an
    even larger channel spread (0.6) than the cube's (0.55), under the same
    directional light and top-down probe geometry (both probes sample each
    object's own top-center point, same surface normal). Rendered through
    the same BGRA-shaped path, its Blue channel would land at index 0 and
    very plausibly exceed the 15-unit margin over indices 1/2 (by the same
    reasoning that produced the cube's own 61-unit spread) — which
    `isReddish()` would then accept via the `asRgba` branch, *because that
    branch only checks "is index 0 dominant," not "is index 0 really Red."*
  - Practical consequence: this specifically undercuts the guard's own
    documented claim — "distinguishes the cube's expected pixel from ...
    the sphere's blue-leaning albedo" (`main.cpp` comment) — for exactly the
    "struct-offset drift severe enough to substitute a neighboring row's
    data" scenario the comment calls out by name. If object index 1's row
    ever reads a stride/offset-shifted view that lands on object index 2's
    (the sphere's) clean row, this probe would very likely still report
    `isReddish() == true` and the gate would falsely PASS. It correctly
    catches the other two scenarios in the same comment (footprint loss →
    floor color, or substituting index 0's row) because those really are
    green/neutral-dominant and legitimately fail the check.
  - I did not modify the (explicitly read-only) worktree to capture the
    sphere's literal runtime bytes; the core claim is a direct, values-
    independent proof from the two boolean expressions plus the confirmed
    real byte order (BGRA), which is sufficient to establish the gap without
    needing that specific number.
