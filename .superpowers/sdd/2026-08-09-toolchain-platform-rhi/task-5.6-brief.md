### Task 5.6 (ad-hoc): Stop requiring a Windows Vulkan loader lib that isn't needed

**Discovered during:** Task 5.5's investigation. `src/rx_platform/CMakeLists.txt:1` calls `find_package(Vulkan REQUIRED)` and links only `Vulkan::Headers` (line ~14) — it never uses `Vulkan::Vulkan` (the loader import library). But CMake's bundled `FindVulkan.cmake` (this install: CMake 3.22) gates `Vulkan_FOUND` — and therefore the existence of `Vulkan::Headers` at all — behind BOTH `Vulkan_INCLUDE_DIR` AND `Vulkan_LIBRARY` being found. There is no headers-only bypass in this CMake version. On this Linux host cross-compiling to Windows, there is no Windows `vulkan-1.lib`/loader import library anywhere, so `find_package(Vulkan REQUIRED)` hard-fails when configuring `windows-cross-zig`, even though nothing in this project actually needs to link the loader.

**Why nothing needs the loader:** the RHI layer (Task 6 onward) uses `volk` for Vulkan function loading — volk resolves Vulkan entry points dynamically at runtime (via the OS's own `LoadLibrary`/`dlopen` of the Vulkan runtime, not a link-time dependency), which is exactly why `rx_rhi_vk`'s planned CMakeLists never links against `Vulkan::Vulkan`/the loader either. The project only ever needs Vulkan *headers* (types, constants, function signatures) at compile time.

**Fix:** replace `find_package(Vulkan REQUIRED)` in `src/rx_platform/CMakeLists.txt` with a direct fetch of the official `KhronosGroup/Vulkan-Headers` repository via `FetchContent` (it is a real, official, header-only repository — provides a `Vulkan::Headers` INTERFACE target via its own `CMakeLists.txt`, no loader library involved at all). Pin an exact tag/commit consistent with the Vulkan 1.3 baseline this project targets (check `vulkaninfo --summary` output already gathered earlier in this project — this machine reports Vulkan Instance Version 1.3.280 — pick a Vulkan-Headers tag at or compatible with 1.3, and verify the tag actually exists before using it, the same way the plan's other dependency pins were verified against real GitHub data rather than guessed). This is a compiled-nothing, header-only dependency — like GLM/VMA/doctest, it does NOT go through the Task-3 `rx_add_cached_dependency` cache mechanism (nothing to cache), just plain `FetchContent`.

**Also check:** whether `SDL3`'s own CMake build (added in Task 5 via the dependency cache) itself calls `find_package(Vulkan)` internally for any of its optional Vulkan-related feature detection, and if so whether that also fails on `windows-cross-zig` — if it does, determine whether SDL3 has a CMake option to skip that probe, or whether it degrades gracefully (SDL3's own Vulkan support is about *detecting* the Vulkan loader at runtime via `SDL_Vulkan_LoadLibrary`, not link-time linking, so it's plausible SDL3's CMake doesn't hard-require `find_package(Vulkan)` to succeed — verify this for real rather than assuming).

**Verification bar:** `windows-cross-zig` must configure AND build cleanly from a fully clean state (`rm -rf build/windows-cross-zig .deps-cache`, matching Task 5.5's verification rigor — this exercises SDL3's cross-build fresh too, not just spdlog). `linux-native` must still configure+build+test cleanly from a fully clean state afterward (`rx_core_tests` and `rx_platform_tests` both passing, including the real Vulkan-instance-extension test from Task 5 — confirm that test still passes for real against this machine's live display/Vulkan driver after switching header sources, not just that it compiles).

Don't assume it's fine just because this task fixed rx_platform's instance of the problem.
