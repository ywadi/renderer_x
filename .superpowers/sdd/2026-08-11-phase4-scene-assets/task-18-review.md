## Deviation adjudication: `MeshBoundsFn` seam instead of hard `asset::Registry&`

**Verdict: correct engineering call, properly justified, not a gate
violation.**

Nothing in the rulings, D19/D24 spec text, or the gate matrix requires a
*hard* `Scene → asset::Registry&` dependency — the brief's own
illustrative `Scene` interface (`task-18-brief.md`) shows no constructor
at all, and the matrix's "Per-instance bounding-box override" /
"Eviction-tolerant handle resolution (D24)" rows specify only the
*behavior* (populate AABB from the mesh's stored bounds; resolve through
the same residency-tolerant path D24 mandates), not the mechanism.
Meanwhile the brief's own "Steps" line is explicit that Task 18 is
device-free end to end ("device-free tests... → implement → commit"),
and `Registry::registerMesh()` — confirmed by grep — is private,
friend-scoped to `import_gltf.cpp`, reachable only through a GPU-backed
`importGltf()`. A hard `Registry&` dependency would have made `Scene`'s
own unit tests unable to exercise real, nonzero-volume AABB transform
math device-free (only the registry's always-invalid fallback mesh would
ever be reachable), which is a real, structural conflict with the task's
own binding scope — not a preference.

The production seam genuinely preserves the D24 contract: this review
read `Registry::mesh()` directly and confirmed it is residency-tolerant
by construction (nonresident-set check, falls back to an always-resident
fallback mesh asset, never null/UB), and `meshBoundsFromRegistry()` is a
verbatim one-line forward (`registry.mesh(mesh).bounds`) with no
caching, no reimplementation, and no logic of its own that could drift
from Registry's own behavior. `Scene::setTransform()` re-invoking the
same `MeshBoundsFn` every call (never caching an `AABB`/`MeshAsset*`) is
exactly the mechanism that makes the D24-at-the-proxy-level test
meaningful, and this review confirmed that test (eviction simulated via
a captured-reference swap) passes and is non-vacuous.

The pattern also matches this codebase's own established
injected-callback idiom (`rx::asset::ImportCompletionFn`), so it is not
a novel abstraction style introduced ad hoc. This is flagged, explained,
and justified exactly the way CLAUDE.md's own convention for
"necessary, not incidental" deviations expects (matching the
`GeometryPool::create()`'s `Allocator&` precedent the report cites).

## Findings

**Critical:** none.

**Important:** none.

**Minor:**
- The "prev-frame transform slot" test (`scene_test.cpp`, "accepts a
  same-shaped 'previous transforms' copy...") is inherently weak: it
  copies `transformsSpan()` into a `std::vector` and checks the copy
  equals itself, which is true of any contiguous span regardless of the
  underlying design's real forward-compatibility. This is not a defect
  in the implementer's work — it is the exact test shape the gate matrix
  itself prescribes for this "preserve-later, do not implement the copy"
  criterion (`matrix-issue05-scene-proxies.md`'s own row: "add a stub
  'previous transforms' array in the test itself and assert it copies
  1:1 with zero reshaping") — but it means this specific line item in
  the gate-hardening checklist is satisfied by definition rather than by
  a meaningfully discriminating test. No action needed; noted for
  awareness when Task 19/the temporal cluster actually build the real
  second column.
- `priority` clamping is tested at its boundaries (default 4, 250→7,
  7→7) but not at a representative in-range non-default value (e.g. a
  desc with `priority = 2` round-tripping to `2`). Low risk — the
  production code path is a single `if (clampedPriority > 7)` guard, so
  an in-range value trivially passes through unmodified — but it is the
  one gap in an otherwise thorough boundary-test set.
