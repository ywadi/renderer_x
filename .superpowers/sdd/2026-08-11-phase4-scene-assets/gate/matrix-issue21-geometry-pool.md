## Conflicts

- **Index width policy: bgfx's 16-bit default vs. D9's unconditional u32.** bgfx (`bgfx.idl`,
  `bgfx.h`, fetched 2026-08-18): static and dynamic index buffers default to 16-bit indices;
  32-bit is opt-in via `BGFX_BUFFER_INDEX32`. RendererX's plan Task 12 (`plan:250-251`): `struct
  MeshRange { uint32_t blockId; uint32_t firstIndex; uint32_t indexCount; int32_t vertexOffset;
  };` and D9 (`design:184`): "Draws use firstIndex/vertexOffset against the shared buffers" — both
  assume a single, uniform, u32-wide index buffer per block with no narrower option ever proposed
  in any Phase 4 artifact. This is not a defect finding (D8/D9 are already-fixed decisions this
  gate does not re-litigate per the brief's own rule), but it IS a genuine divergence from the one
  first-tier engine surveyed that ships an index-width choice at all — recorded here as instructed
  by the matrix format, not resolved.

## New gaps

- **Mixed/16-bit index sub-pools are not registered anywhere in the planning universe.** A sweep
  of `docs/superpowers/specs/*.md` for `16-bit index`, `index width`, `uint16.*ind`, `mixed.*index`,
  `index precision` returned zero hits. D8 (`design:171-173`) explicitly records VERTEX packing
  (1010102-style normal encoding) as "a recorded optimization candidate once meshlets arrive" —
  but says nothing about INDEX width, which is a distinct memory/cache-footprint axis (bgfx treats
  it as significant enough to default to 16-bit). This is a genuine, minor omission, not a
  blocking one: **proposed phase fit is the same phase already named for D8's vertex-packing
  deferral** (the meshlet/geometry phase, per the registry's existing sequencing) — a mixed-width
  index sub-pool (16-bit sub-block for meshes whose vertex count fits, u32 elsewhere) is the same
  class of "packing optimization deferred past Phase 4 simplicity" as the vertex-packing item
  already sitting in that bucket, so no new phase needs to be invented, only the specific item
  named. Not proposed as Phase-4 in-scope: retrofitting non-uniform index width later touches
  `MeshRange` (would need an index-type field) and every draw-record consumer (D26's SoA
  `DrawCommand`/`ViewLists` layout), so if this is ever picked up, it belongs with the other
  packing work rather than being silently assumed cheap.
