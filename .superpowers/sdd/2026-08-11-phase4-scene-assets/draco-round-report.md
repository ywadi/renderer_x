## 1. fastgltf-exposure findings [requirement 2]

Checked directly against the pinned fastgltf v0.9.0 install
(`.deps-cache/fastgltf-*/include/fastgltf/types.hpp`, headers only — the
dep-cache preserves the installed prefix, not the sub-build's source tree,
so this is the actual surface the importer links against):

```cpp
struct DracoCompressedPrimitive {
    std::size_t bufferView;
    FASTGLTF_FG_PMR_NS::SmallVector<Attribute, 4> attributes;
    // findAttribute(name) -- linear scan over {name, accessorIndex} pairs,
    // where accessorIndex here holds the DRACO attribute id, not a glTF
    // accessor index (fastgltf's own reuse of the Attribute struct shape).
};
struct Primitive {
    ...
    std::unique_ptr<DracoCompressedPrimitive> dracoCompression;
};
```

`Extensions::KHR_draco_mesh_compression` exists as a real bit
(`core.hpp:218`) and is wired into fastgltf's extension-string table
(`core.hpp:339,384`). This is exactly the "attribute-id map + bufferView"
surface the ticket asks to verify — fastgltf v0.9.0 parses the extension
natively, no version bump and no self-parsing via extras/extension hooks is
needed. A repo-wide grep for `draco::` calls finds them ONLY in
`import_gltf.cpp` (rx_asset's own consumer code) — never inside fastgltf's
own headers — confirming the intended split: fastgltf parses metadata only,
this project's own code owns every `draco::Decoder`/`draco::Mesh` call.
**Decision: use fastgltf's native parsing as-is (Task 13's own original
choice, re-verified this round) — the least-risk path, and the only one
actually exercised by the working code.**

## 3. Decode path

Unchanged this round. `decodeDracoPrimitive()` (`import_gltf.cpp`
~508-614): reads the compressed bufferView, decodes via
`draco::Decoder::DecodeMeshFromBuffer`, walks `mesh->attribute(id)` for
POSITION/NORMAL/TEXCOORD_0/TANGENT via `findAttr()` (glTF attribute name →
Draco attribute id → `draco::PointAttribute*`), de-indexes into parallel
`positions/normals/uvs/tangents` arrays (one entry per Draco POINT — Draco
already welds identical points) plus a triangle index list, and hands that
to the SAME `processPrimitive()` pipeline (mandatory-attribute defaults →
MikkTSpace tangent generation when absent → meshoptimizer sequence → AABB)
every non-Draco primitive goes through, unchanged. Threading: called inside
the per-primitive `scheduler.parallelFor()` fan-out (`import_gltf.cpp`
~1076-1085) — the identical worker placement as every other accessor read
in that same loop, not a separate mechanism.

### 8.2 Finding 2 — real defect, worse than disclosed, fixed at the decode layer

The disclosed "Attempt 1" revert (bypassing `mapped_index()`) was reported
as a coincidental no-op for the tiny cube fixture. Review correctly
identified this understated the real risk: on BoomBox
(`posAttr->size()` at the time of review, 3237, vs. `numPoints` 3575), the
SAME bypass is a genuine silent out-of-bounds condition — undetected
because the BoomBox test never asserted decoded values, only counts and
`isValid()`.

**Investigating this finding surfaced a second, separate, pre-existing
defect** (not introduced by the review-round's own bypass injection, not
previously known): `findAttr()`'s attribute lookup used
`mesh->attribute(attId)` — an ARRAY-INDEX access — against `attId` values
that are actually Draco's persistent `unique_id()`s (the id
KHR_draco_mesh_compression's own `attributes` map declares, assigned at
ENCODE time). Verified two independent ways this round:
- Reading the vendored Draco decoder source directly.
- A standalone probe (`g++`/zig-c++, linked against this project's own
  vendored `libdraco.a`, built outside this project's test suite) run
  against BoomBox's real compressed payload:
  ```
  num_attributes=4 num_points=3575 num_faces=6036
    attribute[0]: type=GENERIC   size=3575 unique_id=2   (TANGENT)
    attribute[1]: type=POSITION  size=3133 unique_id=3
    attribute[2]: type=TEX_COORD size=3533 unique_id=0
    attribute[3]: type=NORMAL    size=3237 unique_id=1
  ```
  BoomBox's glTF declares POSITION at Draco id 3 — the OLD code's
  `mesh->attribute(3)` returned array index 3, which is actually **NORMAL**
  (a similarly-shaped, unit-vector-scaled VEC3 attribute), not POSITION at
  all. This is exactly why the earlier (pre-fix) render of `sub.bounds` for
  BoomBox came out at ~[-1,1] instead of the file's own declared
  ~[-0.01,0.01] — confirmed a third, fully independent way: Draco's own
  reference `draco_decoder` CLI (built by this project's own dep-cache
  sub-build, entirely outside this importer's code) decoding the extracted
  compressed bytes directly to `.obj`, producing the correct
  ~0.001-0.008-magnitude vertex coordinates. `cube_draco.gltf`'s own
  encode-time ids happen to equal their decode-time array indices
  (0,1,2 — the `TriangleSoupMeshBuilder::AddAttribute()` call order), which
  is exactly why every existing test using that fixture never caught this.

**Both defects fixed in `decodeDracoPrimitive()`** (`import_gltf.cpp`,
commit `340c71d`):
1. Attribute resolution now uses Draco's own purpose-built
   `PointCloud::GetAttributeByUniqueId()` (verified against the vendored
   source: a safe linear scan by `unique_id()`, returns `nullptr` on no
   match) instead of the array-index `attribute(attId)`.
2. Every attribute read (`POSITION`/`NORMAL`/`TEXCOORD_0`/`TANGENT`) now
   goes through a checked wrapper that validates `mapped_index()`'s result
   against the attribute's own `size()` **before** calling `ConvertValue`,
   and inspects `ConvertValue`'s own previously-discarded `bool` return.
   Either violation fails the primitive cleanly via the same
   clear-actionable-error path as a malformed bufferView — never a raw
   indexed read — matching the ticket's own "clear actionable error, never
