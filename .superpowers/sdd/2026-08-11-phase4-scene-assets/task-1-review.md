## Deep-scrutiny findings (the six required traces)

### 1. Ping-pong indexing under frames-in-flight

Traced directly against `executor.cpp`. `++impl.frameCounter` runs at the top of every `execute()` call (`executor.cpp:740`), so call *N* (the *N*th ever) has `frameCounter == N`. `writeSlot = frameCounter % 2`, `readSlot = (frameCounter + 1) % 2` (`executor.cpp:423-424`, and identically in `resolveAttachmentView`/`resolveImageView`/`resolveImage`/`resolveHistoryValid`). Since `(N-1) mod 2 == (N+1) mod 2`, call *N*'s `readSlot` is exactly call *(N-1)*'s `writeSlot` — no off-by-one; this is the intended "read what was last written," not "read what I'm currently writing."

**Empirical proof frame N+1 sees frame N's write, not its own**: reran the GPU test locally (`rx_graph_gpu_tests -tc="*Phase 4 Task 1*"`) — frame 1 writes red to slot 1, reads slot 0 (never written, black-clear only) → readback is exactly the inverted black-clear color (`{255,255,255,255}`), `historyValid() == false`; frame 2 writes green to slot 0, reads slot 1 (frame 1's red) → readback is exactly inverted red (`{0,255,255,255}`), `historyValid() == true`. Frame 2's readback is provably *not* frame 2's own (still-being-written) green — 27/27 assertions passed, reproduced under both the default and the newer Vulkan validation layer.

**Exact guarantee chain for the WAR/WAW hazard across frames (traced, not tested end-to-end under real overlap)**: slot X (= N%2) is written at frame N-2, read at frame N-1, written again at frame N. `applyHistoryAccesses()` feeds all three accesses through the *same, never-reset* `detail::ResourceBarrierState` for that slot (`barriers.cpp:79-165`): frame N-2's write sets `pendingFlushAccess`/`lastWriteStages`; frame N-1's read (layout differs → barrier) flushes it and folds its own stage into `invalidatedStagesUnion`; frame N's write (layout differs again → barrier) finds `hasPendingFlush == false` and takes the WAR path, chaining `srcStage = invalidatedStagesUnion` (frame N-1's read stage) with `srcAccess = 0`. This is a real, correct sync2 execution dependency **provided every `execute()` call submits to the same queue in submission order** — which is exactly the pre-existing assumption this whole executor already rests on for pooled image/buffer cross-frame reuse (`executor.cpp:742-757`'s own comment: "correct as long as callers drive execute() at a pace bounded by real frame-in-flight fencing"). The barrier itself needs no CPU-side fence wait to be correct — Vulkan's same-queue submission-order guarantee is what lets a pipeline barrier recorded in frame N's command buffer synchronize against frame N-1's already-submitted work. A caller's `FrameSync`/fence scheme exists to avoid re-recording into a still-in-flight command buffer (a resource-reuse concern), not to make this specific barrier correct — this task introduces no new reliance beyond what Task 3 already shipped and reviewed.

One caveat, applying equally to every pre-existing cross-frame path in this file, not something Task 1 introduced: every GPU test in `test_execute_gpu.cpp` (old and new) submits via `cmdCtx->runOnce()`, which `vkQueueWaitIdle`s after each call — no test in this codebase exercises genuinely overlapping (pipelined, un-waited) frames-in-flight submission. The barrier reasoning above is sound by direct code trace against `barriers.cpp`'s own already-unit-tested primitive, but the "frames-in-flight = 2, no full wait between" scenario specifically is asserted, not independently reproduced under real overlap, for history *or* for any other resource class in this codebase.

### 2. Never-reset `ResourceBarrierState` reuse — double-emission risk

Traced one full frame's barrier flow for the canonical accumulator pattern (`addHistoryInput("hist") + setHistoryOutput("hist", ...)` on one pass, proven to compile with 2 distinct `ResourceAccess` entries against the same `physicalIndex` in `test_compile.cpp:1607-1646`). `applyBarriers()` (compile-time-derived barriers) explicitly `continue`s on any `isHistory` physical index (`executor.cpp:244-246`) — compile()'s own `allBarriers[pos]` for history physical indices is **never applied**, only ever computed and discarded. `applyHistoryAccesses()` is the *sole* place a history barrier is ever emitted, and it iterates the unmerged per-declaration `accesses` (not `combineByResource()`'s merged view), resolving each access's *own* slot (write slot for `COLOR_ATTACHMENT_OPTIMAL`/`DEPTH_ATTACHMENT_OPTIMAL`, read slot for `SHADER_READ_ONLY_OPTIMAL`) and feeding it to that slot's own `PinnedHistorySlot::barrierState`. For the accumulator pattern this means the read access and the write access resolve to *two different slot objects* with two independent state machines — no merge, no double-emission, no field staleness. Confirmed no other code path ever calls `detail::applyAccess()` against a `PinnedHistorySlot::barrierState` (grep for `applyAccess(` in `executor.cpp` — the only two call sites are `applyHistoryAccesses()` and the hand-written, deliberately-bypassed clear in `initializePinnedHistoryEntry()`).

The persistence itself (constructed once, fed every `execute()` call, never reset) is exactly what realizes contract point 4 — verified there is no other reset path (`acquireHistory()` only resets a slot's `barrierState` on a genuine resize, which is a fresh image and correctly needs UNDEFINED state again).

### 3. `historyValid()` semantics — exact flip point

`PinnedHistorySlot::everWrittenByRealPass` starts `false`, is set only inside `applyHistoryAccesses()`'s `if (isWrite)` branch (`executor.cpp:467-469`) — i.e., only when a real `setHistoryOutput()`-declared access lands, never by `initializePinnedHistoryEntry()`'s black-clear (which touches only `barrierState`, never this field — confirmed by reading the full function, `executor.cpp:529-596`). `resolveHistoryValid()` reads the *read* slot's latch (`(frameCounter+1)%2`), so it answers "has this frame's read slot ever been really written," which is exactly "has one full ping-pong cycle completed." Frame 1 reads slot 0, which has had zero real writes → `false`. Frame 2 reads slot 1, which frame 1 really wrote → `true`. Reran the GPU test locally: `CHECK_FALSE(observedHistoryValid)` after frame 1 and `CHECK(observedHistoryValid)` after frame 2 both pass, and the frame-1 readback is confirmed to be the inverted black-clear color with **zero validation/hazard log lines** under the newer layer (`rx_graph_gpu_tests -tc="*Phase 4 Task 1*" --success`, captured full stdout/stderr and grepped for `hazard|validation|VUID|error|warning` — the only match was the test's own `CHECK_FALSE` success line).

### 4. Pinned-vs-pooled isolation

Read `transient_pool.cpp` in full: `acquireImage()`/`acquireBuffer()` only ever index `images_`/`buffers_`; `sweepStale()` only ever iterates `images_`/`buffers_`; `acquireHistory()` only ever indexes `pinned_` (linear scan by name). No function touches both vectors. `retireAll()` (Executor destructor path, after `vkDeviceWaitIdle`) is the only function that tears down `pinned_`, and it does so identically to how it already tore down `images_`/`buffers_` pre-task (move into a `DeletionQueue`-retired closure, `flushAll()` safe immediately after because the device is already idle) — same, already-proven-safe shutdown pattern, just extended to the third vector.
