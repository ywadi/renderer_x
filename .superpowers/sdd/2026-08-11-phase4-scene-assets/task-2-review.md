## Deep-scrutiny findings (the six required traces)

### 1. Wrapper concurrency correctness (traced against enkiTS v1.12 source, cloned fresh from the pinned tag)

- **`parallelFor` blocking semantics**: `Scheduler::parallelFor` calls `AddTaskSetToPipe()` then `WaitforTask(&taskSet)`. Traced `TaskScheduler::WaitforTask()` (`TaskScheduler.cpp:971-1027`): it loops `TryRunTask()` (which runs *any* available chunk, not specifically the one being waited on) until `pCompletable_->GetIsComplete()`. This is a real blocking wait, not a poll-and-return — `parallelFor()` cannot return before every chunk has actually run.
- **Calling-thread participation**: confirmed by the same trace — the calling thread's `WaitforTask()` is what runs pending chunks "while it waits," exactly as the header documents. Harmless for a lock-free caller: `TryRunTask()` only ever touches enkiTS's own pipes and the caller's `fn`, never anything the caller might be holding a lock on unless `fn` itself takes one (a caller responsibility, same as any parallel-for API).
- **`m_MinRange` timing**: traced `TaskScheduler::AddTaskSetToPipeInt()` (`TaskScheduler.cpp:861-875`) — it reads `m_MinRange` at that call to compute `m_RangeToRun`, not at `TaskSet` construction. Setting `taskSet.m_MinRange = grainSize` before `AddTaskSetToPipe()` is correct, exactly as the code comment claims.
- **Nested `parallelFor` deadlock-freedom**: `WaitforTask()`'s "run pending chunks while waiting" behavior has no notion of "this thread already owns an outer wait," so an inner call's own `WaitforTask()` drains whatever chunks (inner or outer) are available on whichever thread reaches it — confirmed against source, not just plausible. **The nested test genuinely exercises the risky path**: with `workerCount() >= 1`, multiple worker threads concurrently execute their own outer chunks and each independently issues its own nested `parallelFor()` at the same time — multiple live, stack-local `enki::TaskSet` objects contending on the same shared scheduler simultaneously, not a single-thread self-recursion toy case.
- **`postToMain`/`pumpMain` drain strategy**: `pumpMain()` swaps `mainQueue` out under the lock, then runs the swapped copy outside the lock (`scheduler.cpp:680-693`). A `postToMain()` call arriving mid-drain acquires the mutex (now unheld by the swap) and appends to the now-empty `mainQueue`, to be picked up by the *next* `pumpMain()` — never lost, never re-entrant, never blocked on. Correct swap-then-run design.
- **`runOnIoThread` FIFO**: traced `LockLessMultiReadPipe.h`'s `LocklessMultiWriteIntrusiveList` (`WriterWriteFront`/`ReaderReadBack`, lines 227-281) directly — confirmed a genuine FIFO (writers always link at head; the reader always pops from the tail end, i.e., the oldest-linked node first). `IoTask`/`IoLoopTask` both use the default `IPinnedTask` priority (`TASK_PRIORITY_HIGH`), so every `runOnIoThread()` call lands in the *same* per-thread-per-priority list — global FIFO across calls is preserved, not just per-priority.
- **Real bug catch verified against source**: `TaskScheduler::RunPinnedTasks(threadNum_, priority_)` (`TaskScheduler.cpp:956-969`) does `pPinnedTaskSet->Execute()` then dereferences `pPinnedTaskSet` twice more (`m_RunningCount.fetch_sub`, `TaskComplete`) — confirmed a self-`delete this` inside `Execute()` would be a genuine use-after-free on every call. The wrapper's trash-list deferred-reap fix is correct and reaps only after `RunPinnedTasks()` for that cycle has fully returned.

### 2. Teardown semantics (implementer concern 1)

- **No UAF found.** Traced `WaitforAllAndShutdown()` (`TaskScheduler.cpp:1141-1150`): sets `m_bShutdownRequested` before `WaitforAll()`/`StopThreads()`, both called synchronously on the destructing thread; `StopThreads()` joins every internal thread (including the IO thread) *before* it deletes the per-thread pinned-task-list array headers (`TaskScheduler.cpp:503-509`). Since `Scheduler::~Scheduler()` calls `WaitforAllAndShutdown()` explicitly and synchronously in its own body (not relying on implicit member destruction order), the IO thread is fully joined before `impl_`'s own destructor runs. No path was found where a queued closure's *captured* state is touched after being freed elsewhere.
- **Genuine (leak, not UAF) confirmed**: a `runOnIoThread()` task added in the narrow window between the IO thread's last `RunPinnedTasks()` drain of a cycle and the outer loop's shutdown check is never reaped by `IoLoopTask`'s trash mechanism (which only reaps what `RunPinnedTasks()` actually ran) *and* is never referenced by anything after `StopThreads()` deletes the list-header array — the heap-allocated `IoTask` becomes genuinely unreachable. This is a real memory leak (not merely "closure not called" — the raw `new` is never `delete`d through any path), bounded to process-teardown-with-pending-work, matching the report's own disclosed concern. See Quality finding below for the one place this claim is inexact.
- **DeletionQueue precedent check**: read `deletion_queue.h`'s destructor contract directly. It does *not* match cleanly: `DeletionQueue`'s destructor runs the pending items' *captured RAII destructors* as an ordinary side effect of its `std::vector<Item>` being destroyed (nothing is leaked — memory is properly freed, only the closure body itself isn't invoked), **and it logs a loud `RX_LOG_ERROR` naming how many destructors were never flushed**. `Scheduler`'s abandoned `IoTask` is a genuine unreclaimed heap allocation, and it is not logged at all. The report explicitly discloses this divergence ("Unlike DeletionQueue, this is not logged...") rather than hiding it, so this is not a misrepresentation, but "matches the precedent" overstates the parity — see Quality finding.

## Quality findings

**Important** — the `parallelFor` test's `CHECK(distinctWorkersUsed > 1)` assertion is flaky-by-design under CPU contention, and this review reproduced the flake directly (2 failures in 27 runs under `taskset -c 0,1`) rather than treating it as hypothetical. CI (`.github/workflows/ci.yml`, `runs-on: ubuntu-latest`) runs `rx_task_tests` as part of `ctest --preset linux-native` unconditionally, and GitHub-hosted Linux runners are shared, often-throttled 2-4 vCPU machines — squarely the contention regime this review reproduced the failure under. The report's own "Concerns" section discloses the theoretical risk honestly ("a scheduling heuristic outcome rather than an enkiTS API contract") but ships no mitigation: no gate on `std::thread::hardware_concurrency()`/measured parallelism, no retry, no restructuring to force deterministic multi-worker participation. A CI-red flake on an unrelated PR, caused by this test, is a real, foreseeable cost this task leaves unpaid. Recommended fix (either is cheap): skip/relax the `> 1` check when `hardware_concurrency()` is small (e.g. `<= 2`), or replace the heuristic with a deterministic proof — dispatch `workerCount()` `IPinnedTask`s (one explicitly pinned to each worker thread number) that each touch a per-thread flag, which cannot flake regardless of work-stealing behavior.

**Minor** — `runOnIoThread()`'s abandoned-at-teardown `IoTask` is a genuine, silent heap leak (the raw `new` is never `delete`d through any path if the task is caught in the narrow shutdown race the report itself identifies), not merely "the closure body doesn't run." The report frames this as matching `rx::rhi::DeletionQueue`'s teardown precedent; on direct comparison, `DeletionQueue`'s analogous case still runs the captured RAII destructors (no leak) and logs a loud `RX_LOG_ERROR` on non-empty teardown, while `Scheduler`'s case leaks the allocation and logs nothing. The report does disclose this exact divergence ("Unlike DeletionQueue, this is not logged...") rather than hiding it, so this is a documentation-precision nit, not a misrepresentation — but the precedent comparison should be phrased as "matches DeletionQueue's *posture* (non-empty teardown is a caller-timing choice), not its *mechanics* (no leak, loud log)." Low real-world risk given the intended one-Scheduler-per-app, destroy-once-at-process-exit usage, but would trip a LeakSanitizer/Valgrind gate if one is ever added to this CI, and a future fix (tracking outstanding `IoTask` pointers so the destructor can reap them, or at minimum logging the drop count the way `DeletionQueue` does) is cheap.

No Critical findings. The core concurrency mechanism — blocking semantics, calling-thread participation, nested-call deadlock-freedom, `postToMain` drain discipline, `runOnIoThread` FIFO, and the self-delete UAF the implementer caught and fixed — all check out against direct trace of the actual pinned enkiTS v1.12 source, not just the wrapper's own comments about it.
