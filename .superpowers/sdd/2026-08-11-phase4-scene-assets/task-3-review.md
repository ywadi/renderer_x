## Deep-scrutiny findings

### 1. Macro hygiene — verified against real Tracy source, not just the report's paraphrase

- **OFF branch**: `profile.h`'s `#else` block defines all five macros (`RX_ZONE`, `RX_ZONE_NAMED`, `RX_ZONE_DYNAMIC_NAME`, `RX_FRAME_MARK`, `RX_PLOT`) as bare, argument-swallowing no-ops with zero Tracy header dependency — matches Tracy's own `#ifndef TRACY_ENABLE` branch. `tracy_gpu.h`'s OFF branch does the same for its three macros and degrades `GpuProfileContext` to `void*`.
- **Test coverage**: `profile_test.cpp` exercises all five macros unconditionally, including `RX_ZONE_DYNAMIC_NAME` (`dynamicNameFunction`, called with a real runtime `std::string`) — this is the one macro added beyond the brief's named four, and it is covered.
- **Disassembly-level proof, not just `nm`**: rebuilt `rx_core_tests` in a fresh scratchpad OFF configure and disassembled `profile_test.cpp.o` directly. The anonymous-namespace wrapper functions (`zoneScopedFunction`, `zoneNamedFunction`, `dynamicNameFunction`) do not even appear as distinct symbols — they were fully inlined by the optimizer with no residual call, exactly as they would be if the macros had never existed. This is stronger evidence than symbol-absence alone (it rules out "the call exists but the callee optimized to nothing" ambiguity).
- **Dynamic-name idiom is the Tracy-documented one, not the classic misuse.** Verified against the vendored `Tracy.hpp`: `ZoneName(txt,size)` (backing `RX_ZONE_DYNAMIC_NAME`) is `___tracy_scoped_zone.Name(txt,size)` — a per-call method on the zone object created by an *already-active* `ZoneScoped(N)`, which is exactly how every call site here uses it (`RX_ZONE_NAMED("graph_pass"); RX_ZONE_DYNAMIC_NAME(pass.name().data(), pass.name().size());`, same scope, in that order). The wrong approach the review brief flagged — handing a runtime `std::string`'s pointer directly to `ZoneScopedN`'s `name` parameter — is correctly avoided; `ZoneScopedN`/`RX_ZONE_NAMED` is only ever called with string literals in this diff.
- **GPU-side dynamic naming is the matching real idiom too.** `RX_GPU_ZONE_DYNAMIC` expands to `TracyVkZoneTransient(ctx, varname, cmd, nameText, active)`, Tracy's own "Transient GPU zones" mechanism (manual, verified against the vendored `tracy.tex`/`TracyVulkan.hpp` macro table) — not plain `TracyVkZone`, whose `name` parameter is a compile-time literal. Correct choice for a runtime pass name.

**However — the dynamic-name macros do allocate per call, contradicting "no allocations."** See Quality finding 1 below; this was checked precisely because the review brief called it out as the sharpest thing to verify.

### 3. GPU context lifecycle

- **Creation order**: `Executor::create(rx::rhi::Device& device)` calls `createGpuProfileContext(device)` only after `device` is a fully-constructed `Device&` reference — every call site (`samples/05_multipass`, `06_materials`, `src/rx_graph/tests/test_execute_gpu.cpp`'s `GpuFixture`) constructs `device` via `Device::create()` and checks it before ever calling `Executor::create(*device)`. No ordering risk.
- **Teardown order (the UAF question)**: `Executor::~Executor()` calls `vkDeviceWaitIdle(impl_->device)` then `RX_GPU_CONTEXT_DESTROY(impl_->gpuProfileCtx)` (→ `TracyVkDestroy` → `ctx->~VkCtx()`) *before* `Device`'s own destructor can run. Confirmed this ordering is real, not assumed: in every call site that stack-allocates both (`samples/05_multipass:1510/1535`, `:1872/1898`; `06_materials:1173/1198`, `:1455/1481`; `test_execute_gpu.cpp`'s `GpuFixture` struct, `device` at member-position 3, `executor` at member-position 5), `device` is declared/constructed *before* `executor` in every case — C++'s reverse-declaration-order teardown rule therefore destroys `executor` (and its GPU ctx) strictly before `device`. No use-after-free path exists in the code as written.
- **`vkDeviceWaitIdle` before `RX_GPU_CONTEXT_DESTROY` is load-bearing, not decorative**: read `TracyVulkan.hpp`'s `DestroyVkContext`/`VkCtx::~VkCtx()` directly — no null-guard, no idle-check of its own (it tears down a `VkQueryPool` and internal buffers unconditionally). The `vkDeviceWaitIdle` immediately above ensures no in-flight command buffer can still be writing timestamp queries into that pool when it's destroyed.
- **`TracyVkCollect` placement**: confirmed via direct read of `executor.cpp` that every `vkCmdBeginRendering`/`vkCmdEndRendering` pair in `execute()` occurs strictly inside the per-pass loop, and `RX_GPU_COLLECT` is placed after `applyBarriers(..., compiled.finalBarriers(), ...)` at the very end of the function — `finalBarriers()` issues only a `vkCmdPipelineBarrier2`, never a render-pass instance. `cmd` is provably outside a render-pass instance at the `Collect()` call site, matching Tracy's documented requirement.
- **The "real bug caught and fixed" claim is accurate, verified against the actual vendored `VkCtxScope` constructor**: `if (!m_active) return;` runs *before* `ctx->NextQueryId()` (the first dereference) in all three `VkCtxScope` constructor overloads. A hardcoded `active=true` with a null `ctx` (the state `createGpuProfileContext()` returns on `RX_TRACY=OFF` or any creation failure) would indeed null-deref-crash on the very first transient GPU zone. Computing `active` as `(ctx) != nullptr` inside `RX_GPU_ZONE_DYNAMIC` is the correct, necessary fix. Likewise confirmed `TracyVkCollect`'s `ctx->Collect(cmdbuf)` and `TracyVkDestroy`'s `ctx->~VkCtx()` have no built-in null-guard either — `RX_GPU_COLLECT`/`RX_GPU_CONTEXT_DESTROY`'s own internal `if ((ctx) != nullptr)` wrapping is likewise necessary, not defensive-programming theater.
- **Calibrated vs. plain branch**: both macro expansions checked against the real `TracyVkContextCalibrated`/`TracyVkContext` signatures in `TracyVulkan.hpp` — argument count and order match exactly in both branches (6-arg calibrated form, 4-arg plain form, direct-symbol variant since `TRACY_VK_USE_SYMBOL_TABLE` is never defined). The plain branch has no obvious misuse (identical command-pool/buffer setup and teardown structure as the calibrated branch, differing only in which Tracy entry point is called) — **accepted with the disclosure noted**, per the review brief's own instruction: it is genuinely compile-only-verified in this environment (no Vulkan implementation here lacks the extension to force it), but the code itself gives no reason for concern.

### 7. `RX_ZONE_DYNAMIC_NAME` (disclosed deviation)

Justified: the four-macro set named in the original dispatch (`RX_ZONE`/`RX_ZONE_NAMED`/`RX_FRAME_MARK`/`RX_PLOT`) has no mechanism for a per-call runtime name — `RX_ZONE_NAMED`'s underlying `ZoneScopedN` only ever stores the pointer it's given, assuming static storage duration, so handing it a render-graph pass's `std::string`-backed name directly would be undefined behavior the moment that string is ever reused or the pass's own storage changes. `RX_ZONE_DYNAMIC_NAME` is a correct, minimal, well-cited addition wrapping Tracy's own documented per-call idiom (`ZoneName`), used correctly (see finding 1). **Not** a case where the four-macro set should have sufficed instead — the requirement (per-pass zones keyed by a runtime pass name, dispatch item 4) is incompatible with static-literal-only naming. Accepted as designed; see Quality finding 1 for the one real cost this addition carries that the report should have surfaced.

## Quality findings

**Medium — the two added dynamic-name macros allocate on the heap every call, unconditionally, contradicting D3's "passive (~no cost) until a profiler connects" and the brief's "no allocations" cheap-macro constraint.**

Traced directly against the vendored v0.14.0 source (not assumed from the macro name):

- `RX_ZONE_DYNAMIC_NAME` → `ZoneName(txt,size)` → `ScopedZone::Name()` (`TracyScoped.hpp:127-140`): `auto ptr = (char*)tracy_malloc(size); memcpy(ptr, txt, size);` — a real `malloc()` + `memcpy()` on every call.
- `RX_GPU_ZONE_DYNAMIC` → `TracyVkZoneTransient` → the dynamic-name `VkCtxScope` constructor (`TracyVulkan.hpp:594+`) → `Profiler::AllocSourceLocation(...)` (`TracyProfiler.hpp:938-956`): `auto ptr = (char*)tracy_malloc(sz); memcpy(...)` — the same pattern, again per call.
- `tracy_malloc` (`TracyAlloc.hpp:28-39`) resolves to plain libc `malloc()` in this project's configuration (no `TRACY_USE_RPMALLOC`/custom allocator passed in `CMAKE_ARGS`).
- Both allocation sites are guarded only by `if (!m_active) return;`, and `m_active` is `is_active` unconditionally (not gated on "is a profiler actually connected") **because this project deliberately leaves `TRACY_ON_DEMAND` off** (`third_party/CMakeLists.txt`'s own comment: *"D3's 'passive (~no cost) until a profiler connects' behavior is already the plain TRACY_ENABLE-only default this project wants"*). That reasoning holds for `RX_ZONE`/`RX_ZONE_NAMED`/`RX_FRAME_MARK`/`RX_PLOT` (checked directly — all four write only into a lock-free ring buffer, no allocation, regardless of connection state) but **does not hold** for the two dynamic-name macros, which malloc+memcpy every single call regardless of whether a profiler is attached.
- Real-world impact: `Executor::execute()`'s per-pass loop calls both dynamic-name macros once per pass, every frame — with `RX_TRACY=ON` as the *default* in both dev presets, every render-graph pass in every frame now does two small heap allocations (one CPU-side, one GPU-side) that exist purely for profiler labeling, even when no profiler is running. Confirmed non-leaking (`tracy_free` is called by the worker thread after the buffer is consumed/discarded — `TracyProfiler.cpp:699`), so this is a performance/hygiene finding, not a correctness or memory-safety one.
- This is not implementer misuse — `ZoneName`/`TracyVkZoneTransient` are exactly Tracy's own documented mechanism for this exact use case (dispatch item 4 explicitly asked for per-pass zones keyed by a runtime pass name), and there is no allocation-free alternative in Tracy's public API for a genuinely dynamic name. The gap is that the report's own accepted rationale for leaving `TRACY_ON_DEMAND` off ("no cost" per D3) is contradicted by the specific macros this same task added, and this was not caught or disclosed.
- Suggested resolution for a future pass (not a blocker): either enable `TRACY_ON_DEMAND` (which would gate this cost on an actual connection, matching D3's literal text more precisely and costing nothing else, since none of the other four macros' behavior would change), or explicitly disclose the residual per-pass allocation cost as an accepted, bounded trade-off in the design docs. Either is cheap; leaving it silently undisclosed is the actual issue, not the allocation itself.

**Low — `TracyVkCollect`'s "real work" path also runs unconditionally when `TRACY_ON_DEMAND` is off.** Same root cause as the finding above: `VkCtx::Collect()`'s `#ifdef TRACY_ON_DEMAND` early-return (which would otherwise skip query-pool readback when nothing is connected) never compiles in, so every frame's `RX_GPU_COLLECT` call does real `vkGetQueryPoolResults`-class work whenever there are pending GPU zones — which there always are, since `RX_GPU_ZONE_DYNAMIC`'s `active` flag is `true` whenever a context exists, not when a profiler is attached. This is consistent with "always-on Tracy" being an accepted baseline cost (the CPU-side `ZoneScoped` queue-push equivalent is deliberately cheap and accepted the same way), so this is rated Low rather than Medium — it is likely the kind of overhead D3's "~no cost" was already tacitly accepting for the always-on ring-buffer path, just worth naming alongside finding 1 since it shares the same root cause (`TRACY_ON_DEMAND` off) and the same GPU per-pass hot path.

**Informational — plain (uncalibrated) `TracyVkContext` fallback branch is compile-only-verified.** Disclosed honestly in the report; reviewed the code directly and found no misuse (argument count/order match the real macro exactly, identical setup/teardown structure to the calibrated branch). Accepted per the review brief's own instruction — no live driver in this environment lacks `VK_EXT_calibrated_timestamps` to force this path, so it remains an accepted, disclosed residual risk rather than a closed finding.

No Critical or High findings. The GPU-context lifecycle (creation order, teardown order, null-safety of every Tracy-Vulkan macro), the macro-hygiene OFF-path (independently reproduced at the disassembly level), the header-leakage discipline, and the vendoring authenticity all check out against direct trace of the real vendored Tracy v0.14.0 source — not just the report's account of it.

## Quality verdict

**Approved with findings** — 1 Medium, 1 Low, 1 Informational. None blocks merge: the Medium finding is a real, evidenced but narrow and non-leaking performance/disclosure gap (two macros, both required by the dispatch's own per-pass-naming requirement, with no allocation-free alternative in Tracy's API); the Low finding shares its root cause and is arguably within the "always-on Tracy has some baseline cost" envelope the design already accepts; the Informational item is an already-disclosed, already-accepted residual risk. Recommended before this is treated as the final word on Tracy's overhead characteristics: either flip `TRACY_ON_DEMAND` on (cheap, and would close both the Medium and Low findings at once) or add one sentence to `docs/threading.md` or the D3 spec text disclosing that per-pass dynamic naming carries a small unconditional allocation cost whenever `RX_TRACY=ON`.
